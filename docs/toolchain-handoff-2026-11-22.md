# AUTOBLITERATUS toolchain handoff — 2026-11-22

## Scope and distinction

This is a toolchain review of the skipped and unqualified work recorded in `docs/build-progress-2026-11-22.md` and the proposed runtime pairings in `configs/polyglot-runtime-pairings.yaml`.

The tracked implementation is primarily Python, with a standalone C++ SIMD kernel and a React/TypeScript observatory UI. The other language pairings below are **design/status entries**, not existing source trees waiting for a compiler. Tool installation alone will not create those pipelines: each first needs a versioned contract, a dedicated implementation workspace, and the promotion gates in the pairing manifest. Keep them sandboxed, identity-bound, machine-readable, and disabled by default; do not allow a polyglot worker to mutate model state.

## Hardware and vendor stacks not available in this runner

The current machine is Linux x86_64 with native `g++`; `nvidia-smi` and `nvcc` are absent. It is not an accelerator qualification host. For each requested matrix row, use a real compatible machine and record exact hardware, OS/driver, framework/runtime, dtype, model revision, and command:

- **NVIDIA CUDA:** NVIDIA GPU, driver, compatible CUDA runtime/PyTorch build; CUDA compiler/toolkit (`nvcc`) if compiling CUDA sources.
- **AMD ROCm:** AMD GPU, ROCm/HIP, and matching PyTorch HIP build; report ROCm, not NVIDIA CUDA.
- **Apple Silicon/MPS:** macOS Apple hardware and an MPS-enabled PyTorch build; this is separate from generic ARM64 CPU.
- **Intel XPU:** Intel accelerator, driver and matching XPU-enabled PyTorch build.
- **Habana HPU:** Gaudi hardware, SynapseAI and HPU-enabled PyTorch.
- **Huawei NPU:** Ascend hardware, CANN and matching `torch-npu`.
- **AArch64 CPU/NEON:** native ARM64 runner for NEON execution; the current x86_64 run does not provide it.
- **x86_64 CPU/SSE2 or AVX tiers:** this runner provides x86_64 and g++, but no cross-compiler/alternate-ISA qualification. Record the exact CPU ISA and run each intended tier.

Device placement code is not proof of kernel coverage. Quantization conversion, inference, save/reload, and model quality must be tested for every named backend/model combination.

## Non-toolchain blocker: signing and trust roots

Cryptographic manifest signing is still absent. This is not solved by adding a compiler: the repository needs an owner-approved signature algorithm, key custody/location, signing authorization, trust-root provisioning, rotation/revocation, and downstream acceptance policy. After that decision, select a maintained crypto library and implement signature generation plus independent verification tests. Until then, checksums and state fingerprints are integrity evidence only, and manifests must remain explicitly unsigned.
